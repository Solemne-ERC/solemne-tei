The SOLEMNE Encoding Guidelines

About this guide

This is SOLEMNE's encoding guide: how to encode the texts of early medieval canon law in TEI, so that the project's application can import them, and how to read what the application exports. It is also the project's TEI schema: one ODD holds the rules and explains them, and the schema that checks files is generated from it. A change to a rule is made here, in the prose and the specification together.

It is written for someone who has never seen the project's corpus: they can encode a text from scratch, as far as they can reasonably go, check it, and hand it to the import; and anyone can read what an export holds. SOLEMNE, The Social Life of Early Medieval Normative Texts, is a project funded by the European Research Council (grant 101087979) at Radboud University.

Its ten parts go from what a file describes to what an export holds: the file and its header, the text, what is marked in it, records, relations, dates, manuscripts, editions and literature, and exports. The appendices list every element and rule, the code tables and the vocabularies' seeds, older encodings, the import formats' tables, and the changes from one version to the next.

Part VIII's description of manuscripts is modelled on the Bodleian Libraries' TEI P5 Customization and Encoding Guidelines for Manuscript Description (Bodleian Library, Oxford, version 1.0, 2020; the guidelines for medieval manuscripts by James Freeman and Matthew Holford; github.com/msDesc/consolidated-tei-schema), under the Creative Commons Attribution 4.0 licence. Where this guide quotes them word for word, the quotation is introduced as "Oxford encoding guide:".

Must and should, and the checks

The guide says must for what the checks require, and should for what they report or what the guide recommends. The schema checks a file twice:

  • the RelaxNG: the structure, the elements and attributes the schema allows, the closed lists, the forms of pointers and numbers. A file that fails it fails a must, and the import refuses it;
  • the Schematron: the rules that the structure can't express, each with its name. An error is a must; a warning is a should. The import reports both, and imports the file.

An export passes both, without a Schematron error. Appendix B lists every rule, with its check, its severity and its tier; each part shows a counter-example of each of its rules, a fragment that breaks it.

To check a file, install the package (its README says how) and run solemne-tei validate file.xml: it prints each problem with its line, its check, its severity, its rule and its message; --strict makes a Schematron error fail too, as an export must. In Oxygen, a file made from one of the templates is checked as it is typed: the template declares the schema by two xml-model processing instructions, one for the RelaxNG, with the Schematron inside it, and one for the Schematron, for other tools:

<?xml-model href="https://solemne-erc.github.io/solemne-tei/schema/1.2.0/solemne.rng" type="application/xml" schematypens="http://relaxng.org/ns/structure/1.0"?> <?xml-model href="https://solemne-erc.github.io/solemne-tei/schema/1.2.0/solemne.sch" type="application/xml" schematypens="http://purl.oclc.org/dsdl/schematron"?>⚓

The schema is published at its version's address once the release is published; until then, a template is checked with solemne-tei validate.

The boundary and the tiers

A file may state any scholarly claim about the text, its source or the world, at any depth, signed and with its evidence, including pointers to the application's records by permalink, which the import takes as given. Facts that tools establish better, codes, the bounds of a date read from its wording, page breaks joined to images, the identifiers of a text's levels, a file may give too, and they're checked strictly. The application's own state, its nodes' ids, its text versions, change sets, releases, review states and the data it computes, only its exports write, and the guide documents it so that anyone can read an export.

So every element, attribute and rule of the schema has a tier:

  • required: what every file has; without it, a file fails the checks;
  • common: what most encoders add, as most of the project's coded files do;
  • full: every other claim, at full depth;
  • export only: the application's state, which its exports write.

Only the required tier is required, so a minimal file, a rich one and an export pass the same checks. Each part goes from the minimum to the full form, and says each form's tier; appendices A and B give every element's, attribute's and rule's.

The templates

The templates, in the guide's folder templates, are whole files to start from, each a short real text of the corpus but the register, and each checked with the guide's examples:

  • minimal.xml: only the required tier;
  • rich.xml: every common form for a text, and some of the full ones;
  • council-edition.xml: a council, from an edition;
  • collection-edition.xml: a collection, from an edition;
  • decretal.xml: a decretal;
  • penitential.xml: a penitential;
  • manuscript-collection.xml: a collection in one manuscript, with the manuscript's description;
  • reconstruction.xml: a reconstruction, with the witnesses it was made from;
  • export.xml: an export, as the application writes it, with what it adds to an imported file;
  • register.xml: a register of persons, made up, the form of the records the application's database is seeded with.

Principles

  1. The model decides. Where the application's model has a concept, the schema has one form for it; where it has none, the schema doesn't invite one: one element or attribute for each thing, one attribute for pointing to a record, one form of date.
  2. One form in and out. What an export writes, an import reads: an exported file imports again without loss. For each form, the guide says what the import makes of it and what an export writes.
  3. TEI as it is. The guide restricts TEI and documents it, and adds to it only where TEI has no way to say something, saying so: so far, a type on segmentation, a hand's execution on handNote, and a person's type on person.
  4. Closed where the model is fixed, seeded where it grows. The types the application's code relies on are closed lists, which the RelaxNG checks; the vocabularies that grow in the application start from the guide's seeds.
  5. Others' TEI through their own schemas. The Bodleian's descriptions, SCTA's Gratian, the files of the Patrologia Latina and the transcriptions of handwritten text recognition are checked against their own schemas and converted, never let in by widening this one.
  6. Versioned. Every release says what changed, and whether files that passed may now fail: a major version where they may, a minor one for additions, a patch for the prose.

Two ways through the guide

A first file. To encode a text from scratch, read in this order, starting from the minimal template:

  1. I.1 Documents and nodes and I.2 The levels of a text;
  2. II.1 The title statement, II.1.1 Categories and types and II.1.2 The coding rules;
  3. II.3 Publication and source;
  4. III.1 Divisions, III.2 Headings and III.3 Numbers;
  5. III.10.1 Editions and manuscripts, III.10.2 Page breaks and III.10.5 Gaps and lacunae;
  6. IV.1 Names and their records, IV.3 Statements, references, quotations, formulae, IV.4 Sources and the pointers' forms and IV.5 Notes: sources, parallels, reception, attributions, editorial remarks, as far as the file goes;
  7. II.4.2 Curation; then check the file (Must and should, and the checks).

Reading an export. To read what the application writes:

  1. I What a file describes, all of it;
  2. II.1 The title statement, for the levels' permalinks, and II.6 The history of the file;
  3. III The text;
  4. IV What is marked in the text, with IV.8.1 Fragments and IV.8.2 Anchors;
  5. V Records, VI Relations, VII Dates and IX Editions and literature;
  6. X Exports, with the template export.xml.
